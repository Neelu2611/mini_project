# Implementation roadmap

Each phase requires its acceptance criteria before the next dependent phase proceeds. Application work begins after approval of this plan.

| Phase | Work | Tests and acceptance criteria |
|---|---|---|
| 1. Audit and plan | Review the notebook and inventory files. Document the target, features, model, risks and proposed scope. | Verify the five planning files, original notebook hash, exact ordered 47-field contract and final metric sources. Review this plan and confirm the notebook revision before using it as the implementation baseline. |
| 2. Verify the supplied artifact | Record provenance, verify the fitted feature contract, and test compatible de-identified records or labelled synthetic fixtures. Historical training dataset verification is deferred. | In a compatible Python environment, verify bundle loading, fitted types, 47 ordered inputs, 2,396 transformed features and classes 0/1/2. Check labels, probability order and parity against direct calls on the fitted objects. Obtain user approval before Phase 3. |
| 3. Implement Python inference and API | Scaffold FastAPI and Pydantic, load the artifact once, implement normalization and model metadata, and expose typed health and predict routes. | Test all keys and aliases, nullable lab handling, literal `?`, exact diagnosis strings, integer validation, missing and extra fields, categorical validation and probability/class alignment. Exercise real-bundle parity directly and through HTTP. Verify readiness and prediction failure on missing or invalid artifacts, multi-request stability, and absence of raw payloads from logs. |
| 4. Build frontend and integrate | Set up Next.js, Tailwind and shadcn/ui, generate types from OpenAPI, and build overview, prediction, model and methodology pages. | Run type checks, lint and a production build. Test keyboard navigation, focus and labels, responsive layout, validation, timeouts, unavailable state and clearing stale results. Confirm form groups serialize all expected keys and the result displays the exact class and scores returned by Python. |
| 5. Verify end to end and hand off | Lock dependencies, document local setup and artifact provisioning, run full verification and prepare an academic demonstration. | Start both services in a clean environment. Submit a synthetic encounter through the browser and compare the displayed result with direct Python inference on the same input. Confirm a second encounter replaces the previous result and that backend outage shows an error without a result. Verify chart labels and counts against metric sources, privacy behavior and operation without the CSV once inference assets are provisioned. |

Use synthetic or de-identified fixtures only. Generate expected predictions from the trusted model. Artifact-dependent tests must be reported as blocked when the model is absent. If offline parity evidence is incomplete, record exactly what was checked and which metric or compatibility claims remain provisional. Request explicit approval before regenerating the fit. Any deployment beyond the local academic demonstration is a separate scope decision.
